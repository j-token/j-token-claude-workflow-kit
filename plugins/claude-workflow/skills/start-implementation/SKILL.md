# 구현 작업 시작하기

## 출력 언어

사용자가 출력 언어를 명시적으로 지정하면 해당 언어를 사용합니다. 지정하지 않으면 이 스킬이 만드는 모든 사용자 대상 출력, 문서, 프롬프트, 보고서, 계획, 스펙 및 기타 산출물을 한국어로 작성합니다. 제목, 섹션, 레이블, 표, 체크리스트, 다이어그램, 템플릿에도 같은 언어를 사용합니다. 코드, 명령어, 파일 경로, 식별자, API 이름, 모델 ID, 프로토콜 이름과 필수 고유명사는 번역하지 않습니다.

## 작성 문서 첨부

요청된 모든 문서의 작성 또는 갱신을 마친 뒤 최종 응답에 각 문서를 `[문서 이름](절대 경로)` 형식의 Markdown 링크로 반드시 첨부합니다. 링크에는 독립된 디렉터리 세그먼트로 구성된 절대 경로를 사용하고, 디렉터리 구분자를 생략하거나 경로 세그먼트를 붙여 쓰지 않습니다. Windows 경로를 문자열로 표시할 때는 `C:\\Users\\WinUser\\Documents\\폴더\\문서.md`처럼 각 역슬래시를 두 번 씁니다.

## SHA-256 표기

- PRD와 기술 스펙의 전체 SHA-256은 파일 동일성 검증을 위해 내부적으로 계산·비교합니다. Bash 등에서 `sha256sum` 또는 동등한 명령을 사용합니다.
- 사용자 대상 응답, 문서, 표와 인계 설명에는 대문자 기준 `앞 4자리…뒤 4자리`만 표시합니다. 예: `ABCD…1234`.
- 축약 표시를 실제 전체 해시 비교의 대체물로 사용하지 않습니다.

확정된 문서를 다시 읽고, 필요한 검증을 계획한 뒤 plan 모드로 구현을 시작합니다.

## 시작 게이트

다음 조건을 모두 확인합니다.

1. 구현 기준이 되는 기술 스펙, 버그 리포트 또는 UI 구현 문서의 경로와 버전(있으면)이 확인되어야 합니다. PRD는 기술 스펙의 입력이므로 제품·기능 구현의 기준 문서로 사용할 수 없습니다.
2. 해당 문서를 현재 또는 이전 assistant 응답에서 사용자에게 제시한 뒤, 그 응답을 끝냈어야 합니다.
3. 문서 제시가 끝난 뒤의 별도 사용자 메시지에서, 사용자가 그 문서의 구현·수정·디버깅 시작을 명시적으로 승인해야 합니다.
4. 문서에 반영되지 않은 사용자 피드백이나 구현을 막는 사용자 결정 사항이 없어야 합니다.
5. 제품·기능 기술 스펙은 `audit-technical-spec`이 만든 감사 보고서의 판정이 `통과` 또는 `조건부 통과`이고 블로커가 없어야 합니다. 감사 보고서의 스펙 절대 경로·버전·축약 SHA-256과 승인된 PRD 절대 경로·버전·축약 SHA-256이 현재 파일들과 일치해야 합니다. 중요 발견은 구현 TODO·테스트·ADR·spike 또는 영향 영역 보류 조건으로 인계합니다. 이 조건은 버그 리포트와 UI 구현 문서에는 적용하지 않습니다.

승인으로 인정하는 표현은 문서 경로 또는 버전을 다시 확인한 `승인`, `이 문서대로 구현 시작`, `이 버전으로 수정 시작`처럼 명시적인 후속 응답입니다. 최초 요청의 `작성 후 구현해줘`, `먼저 문서화하고 수정해줘`처럼 문서 작성과 구현 의사를 한 문장에 둔 표현은 구현 의사로만 기록하며 승인으로 인정하지 않습니다. 조건을 충족하지 못하면 구현을 시작하지 않습니다. 에이전트의 성능을 미확정 요구사항의 대체재로 사용하지 않습니다.

## 문서 제시와 승인 대기

문서 작성 스킬은 문서를 사용자에게 제시한 뒤 다음처럼 승인 대상 경로를 다시 확인하고 현재 턴을 종료합니다.

```text
문서: <문서 경로> (<버전 또는 상태>)
이 문서대로 구현을 시작하려면 다음 메시지에서 `승인` 또는 `이 문서대로 구현 시작`이라고 알려주세요.
```

그 응답 뒤에는 코드 수정, plan 모드 진입, 후속 구현 계획을 진행하지 않습니다. 별도 사용자 메시지가 오면 승인 대상이 제시한 문서와 일치하는지 먼저 확인합니다.

## 문서 재확인

구현을 시작하기 직전에 구현 문서를 파일에서 한 번 다시 읽습니다. 제품·기능 작업이면 승인된 PRD의 경로를 기술 스펙과 감사 보고서에서 확인하고 PRD도 다시 읽습니다. PRD와 기술 스펙의 전체 SHA-256을 모두 다시 계산하고, 감사 시 보존한 전체 값이 있으면 전체 값으로 비교하며 사용자 문서의 축약 fingerprint도 확인합니다. 이전 대화의 요약이나 기억만으로 구현하지 않습니다.

기술 스펙 작업이면 현재 PRD와 스펙 파일의 전체 SHA-256을 다시 계산하고 감사 보고서의 축약 fingerprint와 비교합니다. 하나라도 다르거나 블로커가 남아 있으면 구현을 시작하지 않습니다. 핵심 계약이 변경됐다면 변경된 계약과 직접 영향 범위만 `audit-technical-spec`으로 재감사한 뒤 변경 문서를 별도 사용자 메시지에서 다시 승인받습니다.

다음 항목을 추출해 구현 계획의 근거로 삼습니다.

- 변경 범위와 예상 파일/모듈 수
- 요구사항의 명확성과 남은 설계 판단
- 외부 시스템, 도구, 플랫폼의 수
- 검증 단계와 실패 재현 난이도
- 보안, 데이터 손실, 배포, 호환성 같은 실패 비용
- 서로 독립적으로 나눌 수 있는 작업의 존재
- 기술 스펙인 경우 감사 보고서의 판정, 대상 경로, 버전, 축약 SHA-256과 미해결 발견
- 제품·기능 작업인 경우 승인된 PRD의 절대 경로, 버전과 축약 SHA-256

## 구현 범위 산정

구현 강도는 판단의 수·상호작용·실패 비용을 기준으로 정합니다. 파일 수만으로 강도를 높이지 않습니다.

- 완료 조건이 명확하고 절차가 반복 가능한 좁은 변경은 국소 수정과 정형 변환으로 처리합니다.
- 요구사항이 확정되어 있고 여러 파일·도구·일반 검증이 필요한 일상적 구현은 표준 다중 파일 구현으로 처리합니다.
- 아키텍처 판단, 여러 시스템·플랫폼 상호작용, 어려운 원인 분석, 보안·데이터·호환성 위험처럼 깊은 판단이 필요한 구현은 단계를 나누고 각 단계 후 검증합니다.

구현을 하위 에이전트로 분해할지는 `orchestrate-subagents`의 생성 게이트로 별도 평가합니다. 다만 구현 직전 문서 논리 검토와 구현 직후 코드 리뷰는 선택적 분해가 아닌 필수 독립 검증입니다.

## 구현 작업의 필수 독립 검증

구현은 일반 구현 분해 여부와 관계없이 다음 두 체크포인트를 모두 수행해야 합니다.

1. **구현 직전 문서 논리 검토**: 제품·기능 작업은 PRD, 기술 스펙, 감사 보고서와 최신 사용자 지시를, 버그·UI 작업은 승인 문서와 최신 사용자 지시를 새 컨텍스트의 읽기 전용 Agent 한 명에게 전달합니다. 엣지 케이스, 논리 오류, 요구사항 간 충돌, 문서와 저장소 간 충돌과 빠진 실패 경로를 조사하게 하고, 루트가 근거를 검증합니다. 실제 구현을 시작할 수 없거나 핵심 요구사항·데이터·보안·호환성을 위반하는 `블로커`만 문서 작성 작업으로 돌려보냅니다. 중요·경미 발견은 구현 TODO·테스트·ADR·spike로 이관하고 구현을 시작합니다.
2. **구현 직후 코드 리뷰**: 구현과 1차 검증이 끝난 뒤, 최종 완료 보고 전에 첫 검토와 다른 새 컨텍스트의 읽기 전용 Agent 한 명에게 승인 문서, 변경 diff, 관련 코드와 테스트 결과를 전달합니다. 로직 오류, 엣지 케이스, 회귀, 오류 처리, 보안·호환성 문제와 빠진 테스트를 검토하게 합니다. 루트가 유효한 발견을 수정하고 관련 검증을 다시 실행합니다. 리뷰 대응으로 동작 코드나 테스트가 바뀌면 이전 리뷰와 다른 새 무컨텍스트 Agent에게 변경된 최종 diff를 다시 리뷰시킵니다. 블로커와 중요 발견이 0개인 `통과` 결과가 나올 때까지 반복하며, 새 리뷰 Agent를 생성할 수 없으면 완료로 보고하지 않습니다.

두 Agent에는 현재 대화 내용이나 루트의 예상 결론을 전달하지 않습니다. 원본 문서 경로, 저장소 경로, 사용자 최신 지시, diff와 검증 결과처럼 독립 검토에 필요한 자료만 제공합니다. 두 검토의 프롬프트, 판정 계약과 심각도 정의는 `orchestrate-subagents`의 필수 독립 검증 프롬프트를 그대로 사용합니다. 두 프롬프트 모두 `수정 허용 파일: 없음`, `수정 금지 파일: 모든 파일`을 명시합니다. Agent(Task) 툴이 없거나 에이전트를 생성하지 못하면 루트가 대신 검토한 것으로 간주하지 말고 구현을 시작하거나 완료로 보고하지 않습니다.

## 구현 진입 (plan 모드)

Claude Code에는 새 최상위 스레드를 시작하는 도구가 없으므로, 구현은 현재 세션에서 plan 모드 게이트를 통해 시작합니다.

1. 승인 문서와 사용자 요청에서 구현 목표, 수행할 일, 금지 사항, 제약·결정 사항을 추출합니다.
2. 구현 코드를 수정하기 전에 **구현 직전 문서 논리 검토** Agent를 생성하고 결과·근거를 검증합니다. 유효한 블로커가 남으면 구현을 시작하지 않고 문서 작성 단계로 돌려보냅니다.
3. `EnterPlanMode`로 plan 모드에 진입해 확정된 문서와 감사 보고서를 기준으로 구현 계획을 제시합니다. 계획에는 변경 대상 파일, 구현 순서, 검증 방법, 두 필수 독립 검증 수행 지점을 포함합니다.
4. plan 모드에서는 코드를 수정하지 않고 계획만 제시합니다. `ExitPlanMode`로 사용자에게 계획을 승인받기 전까지 구현을 시작하지 않습니다.
5. 사용자가 계획을 승인하면 plan 모드를 빠져나와 현재 세션에서 구현하고, 변경 후 관련 검증을 수행합니다.
6. 구현과 1차 검증이 끝나면 **구현 직후 코드 리뷰** Agent를 생성하고 결과를 검증·반영·재검증합니다. 블로커·중요 0개 `통과`가 나올 때까지 반복한 뒤에만 완료를 보고합니다.
7. 최종 보고에 구현 직전 문서 논리 검토와 구현 직후 코드 리뷰의 Agent 생성 여부, 발견, 반영과 재검증 결과를 각각 포함합니다.

이 절차는 문서 열람만으로 작업을 끝내지 않고 구현·검증·보고를 완료하게 합니다. 승인된 문서와 사용자 요청이 충돌하면 사용자의 최신 명시 지시를 우선합니다. 문서 밖의 구현 방식·작업 범위를 임의로 추가하지 않습니다.

## 실패 처리

- `EnterPlanMode`를 사용할 수 없으면 코드를 곧바로 수정하지 않고, 구현 계획을 사용자에게 제시한 뒤 명시적 승인 후 구현합니다.
- Agent(Task) 툴이 노출되지 않아 필수 독립 검토를 수행할 수 없으면 루트가 대신 검토한 것으로 간주하지 않습니다. 구현 시작 또는 완료 게이트가 충족되지 않았음을 보고합니다.
- 검토 Agent 생성 호출 오류, 중단·무응답 또는 대기 실패가 발생하면 동일한 원본 입력과 새 컨텍스트로 한 번만 재시도합니다. 다시 실패하면 해당 게이트를 미충족으로 남기고 완료로 보고하지 않습니다.
- 프로젝트를 찾지 못하거나 문서 경로를 읽을 수 없으면 먼저 그 문제를 해결합니다.

## 동작 확인 시나리오

| 시나리오 | 기대 결과 |
| --- | --- |
| 사용자가 `문서 작성 후 구현해줘`라고 최초 요청 | 문서를 작성·제시하고 승인 안내를 남긴 뒤 현재 턴을 끝낸다. 코드 수정과 plan 모드 진입은 하지 않는다. |
| PRD 제시 뒤 사용자가 구현을 승인 | 제품·기능 구현 기준 문서가 아니므로 구현하지 않고 기술 스펙 작성 단계로 안내한다. |
| 감사하지 않은 기술 스펙의 구현을 승인 | 구현하지 않고 `audit-technical-spec`으로 무컨텍스트 하위 에이전트 감사를 먼저 시작한다. |
| 감사 판정이 `차단` | 블로커에 필요한 최소 계약만 기술 스펙에 반영하고 변경된 계약과 직접 영향 범위를 새 SHA-256으로 재감사할 때까지 구현하지 않는다. |
| 감사 판정이 `조건부 통과` | 중요 발견을 구현 TODO·테스트·ADR·spike 또는 영향 영역 보류 조건으로 인계하고 블로커가 없으면 구현 진입을 진행한다. |
| 감사 뒤 핵심 계약이 변경됨 | 변경된 계약과 직접 영향 범위를 새 SHA-256으로 재감사한다. 표현 정리나 구현 TODO 변경만으로 전체 재감사하지 않는다. |
| 문서 제시 뒤 사용자가 `승인`이라고 응답 | 제시한 문서가 하나로 식별되면 구현 진입 절차를 시작한다. 식별되지 않으면 문서 경로 또는 버전을 확인한다. |
| 문서 제시 뒤 사용자가 다른 문서의 구현을 요청 | 승인 대상이 다르므로 해당 문서를 제시·확정하는 흐름으로 돌아간다. 기존 문서를 승인으로 재사용하지 않는다. |
| 구현이 코드 수정을 시작하려 함 | 먼저 새 컨텍스트의 문서 논리 검토 Agent를 생성하고 결과·근거를 검증한다. 유효한 차단 사항이 남으면 구현하지 않는다. plan 모드 계획을 승인받기 전에는 코드를 수정하지 않는다. |
| 구현과 1차 검증이 완료됨 | 첫 검토와 다른 새 컨텍스트의 코드 리뷰 Agent를 생성하고 결과를 검증·반영·재검증한 뒤에만 완료를 보고한다. |
| 필수 검토용 Agent 툴이 없음 | 루트 검토로 대체하지 않고 구현 시작 또는 완료 게이트가 충족되지 않았다고 보고한다. |
